# 游戏测试规范

1. **测试策略选择**：开发功能前，由 AI 根据需求自主判断测试方式
   - **TDD**：规则明确、预期结果可自动验证的功能，优先用于数值计算、状态机、资源管理及复杂业务逻辑
   - **开发后测试**：视觉表现、动画、操作手感等探索性功能，先开发再补充适用的自动测试
   - **混合模式**：同时包含确定性逻辑与动态表现的功能，分别采用对应方式
   - **Bug 修复**：能够自动复现时，优先编写失败测试，再修复问题
   - 在开发计划中简要说明选择结果及原因

2. **TDD 执行流程**：采用 Red → Green → Refactor 小步循环
   - Red：先编写测试，确认测试因目标功能缺失而失败
   - Green：编写满足测试的最少代码，使测试通过
   - Refactor：在保持测试通过的前提下优化代码
   - 重复循环，逐步完成整个功能

3. **测试脚本管理**：
   - 优先复用现有测试脚本，覆盖不足时再新增
   - 遵循项目目录规范，不创建无实际验证价值的测试

4. **测试质量**：
   - 测试必须验证明确的预期行为，覆盖关键正常、边界及异常情况
   - 不得仅以运行无报错判定通过，不得以现有实现代替需求作为预期结果

5. **回归测试**：
   - 功能修改后，分析代码调用、信号、场景及资源依赖，执行当前模块及受影响模块的测试
   - 新增测试应纳入后续回归测试

6. **错误修复**：
   - 测试失败时定位并修复根因，重新执行失败测试及相关回归测试
   - 不得通过删除测试或放宽断言掩盖错误。若需求发生变化，应先确认预期再调整测试

7. **测试边界**：
   - 优先执行可自动验证的测试
   - 无法自动验证的视觉、手感及复杂交互交由人工验收，不以自动测试通过代替人工验收

8. **最终验证**：
   - 合并任务或正式导出前，执行完整自动测试集
   - 无法执行、未通过或无法修复的测试必须明确报告，不得声称全部通过
