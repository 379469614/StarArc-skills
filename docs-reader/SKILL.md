# 项目文档阅读

## 核心原则
- **读设计读文档，读实现读代码**：设计意图、规则、数值口径来自文档；类名、节点路径、函数名、信号签名、`@export` 参数等结构信息直接查代码——文档里本来就不该有这些，用文档回答结构问题只会得到过期答案
- **术语以术语表为唯一基准**：所有文档必须遵循 `00_总览与术语.md` 的术语；文档内出现与术语表冲突的表述时，以术语表为准并向用户报告该冲突
- **冲突不单方面裁决**：文档与代码行为不一致时，把「代码现状」和「文档预期」一并报给用户确认，不擅自改文档、也不擅自改代码
- **文档缺失不等于设计缺失**：找不到对应文档时，按代码现状继续推进，但必须明确声明"文档未覆盖该项"，禁止编造设计
- **只读不写**：本技能不修改任何文档；需要落盘一律交给 `docs-organizer`，读写职责分离
- **最小读取**：先锁定本次任务涉及的模块，只读相关文档，不全量通读

## 文档目录定位
- 以 `project.godot` 所在路径为标准，找到的该文件所在目录即为项目根，文档目录固定为 `<项目根>再上一层的目录/1项目文档/`，对应为 `../1项目文档`
- 找不到 `project.godot`，或文档目录不存在 → 停止并询问用户项目根位置，不凭猜测读取
- 存在多个候选工程时，取当前工作目录向上最近的 `project.godot`；仍有歧义则询问用户

## 读取顺序与范围
按由粗到细的顺序逐级深入，只读本次任务真正需要的层级：

1. `00_总览与术语.md` —— 术语基准，任何任务都先读
2. `01_核心循环.md` —— 仅当任务涉及流程或状态流转时读
3. `04_数值框架.md` —— 仅当任务涉及数值、经济或成长时读
4. `02_系统设计/`、`03_玩法设计/`、`05_全局服务/` —— 只读与本次任务相关的单篇文档

- 先列出候选文档清单再决定读哪篇，不整目录通读
- 文档较长时，先用检索定位相关小节标题，只读命中段落，控制 token 消耗

## 输出内容
阅读完成后，按以下顺序向用户输出（中文、简洁、遵守全局的有序清单规范）：

1. 相关现状 —— 本次任务涉及系统的当前设计，并标注来源文档名
2. 术语口径 —— 本次会用到的术语
3. 约束与边界 —— 文档中限制实现方式的规则
4. 冲突与缺失 —— 文档与代码不一致处、文档未覆盖项
5. 需确认事项 —— 影响设计结论且当前资料无法确认的问题

- 每一条都必须说明信息来源，便于用户核对；没有问题的类别不输出空标题

## 异常与冲突处理
- **文档目录或某文档缺失**：如实报告缺失项，继续按代码现状推进；不新建文档（新建属于 `docs-organizer`）
- **文档之间互相矛盾**：以 `00_总览与术语.md` 与单一事实来源文档为准，并把矛盾点报给用户
- **文档陈述与代码行为不一致**：以代码实际行为描述"现状"，以文档描述"预期"，两者并列报给用户确认
- **确认后需要落盘**：交 `docs-organizer` 修改文档，本技能不动手

## 与其他技能的衔接
- 任务开始前 → 本技能（读现状）
- 工作落盘后 → `docs-organizer`（更新文档）
- 新增文件 → `folder-structure`；`.gd` 改动 → `gdscript-style`；涉及玩家可见文本 → `multilingual`；UI 相关 → `ui-style`
- 本技能为纯只读操作，因此在 Plan 模式下同样可用

## 常见误区
- 把文档里的"建议""可以"当作硬性规则去执行
- 用文档中的业务词去反推代码结构，而不是直接读代码
- 为了"读全"而通读全部文档，浪费 token 且引入无关约束
