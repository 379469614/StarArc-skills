# 项目文档读取

## 技能目标

在开始分析、设计、制定计划或回答依赖项目现状的问题前，先读取相关项目文档了解既有设计与约束，避免结论偏离项目现状；随后按需查询相关代码确认实际实现；若发现文档设计意图与代码实际行为存在实质冲突，则暂停相关结论并向用户确认以哪一方为准

## 核心原则

- **先读设计，再做方案**：进行分析、设计或制定计划前，先了解与当前需求相关的既有设计
- **文档看意图，代码看现状**：文档用于确认设计目标、规则和系统关系；代码用于确认当前实际实现
- **冲突不擅自判断**：若文档设计意图与代码行为明显不一致，向用户说明差异并确认以哪一方为准
- **单一事实来源**：同一设计存在多个描述时，优先找到其正式定义位置，不将重复描述同时视为独立规则
- **术语一致**：以 `00_总览与术语.md` 中定义的术语作为理解基准
- **最小必要读取**：只读取完成当前任务所需的文档和代码，不遍历无关内容

## 文档路径

- 以 `project.godot` 所在目录作为项目根
- 项目文档固定位于 `../1项目文档/`
- 找不到 `project.godot` 或文档目录时，不猜测位置，向用户确认

## 执行流程

1. **文档发现**：扫描 `../1项目文档/` 的目录与文件名，不先读取全部正文
2. **定位相关文档**：根据当前需求判断需要了解的系统、玩法、流程、数值或全局服务
3. **读取术语**：涉及游戏设计内容时，读取 `00_总览与术语.md` 作为术语和全局规则基准
4. **读取设计**：读取与当前需求直接相关的文档，明确既有设计意图、规则、约束及系统关系
5. **查询代码**：需要确认当前实现时，再定位并读取相关代码，不使用代码结构反推不存在的设计规则
6. **一致性检查**：
   - 实现细节不同但设计行为一致 → 继续，以代码作为当前实现参考
   - 文档缺失但代码已有实现 → 将其视为当前实现事实，不自行推断设计意图
   - 文档规则与代码行为存在实质冲突 → 暂停依赖该事实的设计或计划，向用户说明双方差异并询问以哪一方为准
7. **继续任务**：用户确认后，将确认结果作为本次分析、设计和计划的事实基准

## 冲突判断

只有会影响设计结论、玩家行为、规则、流程、数值或系统职责的差异才需要询问用户

代码文件位置、节点结构、函数名、变量名、信号、实现方式等技术细节差异，不属于设计冲突
