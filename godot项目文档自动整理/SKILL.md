# 项目文档自动整理

## 一、核心原则

1. **只写设计，不写实现。** 文档回答"为什么这样设计""各系统怎么协作"，**不记录**脚本路径、节点路径、函数名、变量名、信号签名、`@export` 参数、uid 引用等代码结构信息——那些读代码就能得到，写进文档只会加速过期。
2. **用玩家和策划的语言描述。** "玩家生命值归零时进入结算流程"，而不是 "HealthComponent 发射 died 信号"。
3. **单一事实来源。** 每条设计只在一个地方定义，别处引用它。同一条规则在两篇文档里说法不同 = 文档已失效。
4. **不确定的不写死。** 实验性、待验证的内容标注为"草案 / 待验证"，不写成既定设计。
5. **设计是意图，实现是现状。** 二者冲突时以已实现的效果为准更新文档，但要把差异记进变更日志并提示用户。

## 二、文档根目录定位（先定锚点，再动手）

1. 从当前目录**向上查找 `project.godot`**，找到的目录即为项目根，文档目录固定为 `<项目根>/1项目文档/`。
2. 找不到 `project.godot` → 停止并询问用户项目根位置，不凭猜测写。
3. **多项目管理**：每个游戏各自维护自己的 `1项目文档/`。若多个游戏共用底层框架或公共库，公共设计单独放在 `1项目文档/0-公共/`，各项目用相对链接引用，**禁止复制**，复制必然失同步。

## 三、触发时机与变更范围判定

- **何时触发**：一轮任务收尾时执行一次；用户显式要求时执行。**多步任务不要每改一个文件就更新一次。**
- **改了什么**：优先用 `git status` / `git diff --stat` 确定变更范围；无 git 时按本次会话实际改动记录。
- 只更新**受影响的文档**，不做全量重写。

## 四、分级处理策略（避免过度维护）

| 级别 | 判定标准 | 动作 |
|---|---|---|
| **L1 轻量** | 数值微调、文案修改、局部缺陷修复、表现层优化 | 只在 `5-变更日志/` 追加一行，**不动设计文档** |
| **L2 中量** | 新增或调整某个玩法系统、改动规则或数值框架、调整系统间协作方式、内容结构变更 | 更新对应系统设计文档 + 索引登记 + 变更日志 |
| **L3 重量** | 核心玩法变更、游戏流程改造、全局服务增删、系统职责边界重划、存档策略变更 | 更新架构/设计文档 + 新增 ADR 决策记录 + **必须先向用户确认再写** |

## 五、目录结构（首次使用时按此骨架创建，缺失补齐，不推倒重建）

```
1项目文档/
├── README.md                 # 索引与导航，AI 首先读它
├── 0-设计/
│   ├── 游戏概述.md           # 一句话卖点、目标平台、受众、参考作品
│   ├── 核心玩法.md           # 核心循环、规则、胜负条件、节奏曲线
│   ├── 数值框架.md           # 属性维度、成长曲线、经济循环、平衡基调
│   ├── 表现风格.md           # 美术与音频风格、反馈基调
│   └── 叙事与世界观.md       # 无叙事需求可标注"不适用"
├── 1-架构/                   # 描述"系统怎么协作"，不是代码怎么组织
│   ├── 系统总览.md           # 系统清单、职责边界、依赖方向
│   ├── 系统交互.md           # 谁在什么时机通知谁、为什么用广播
│   ├── 游戏流程.md           # 玩家视角的流程与状态流转
│   └── 进度与存档.md         # 存档内容、版本策略、跨版本兼容原则
├── 2-系统/                   # 一个玩法系统一篇：战斗系统.md、背包系统.md ...
├── 3-内容规范/               # 内容分类维度、命名约定、素材规格
├── 4-决策记录/               # ADR-0001-用事件总线解耦UI.md + README.md 列表
└── 5-变更日志/               # 按月份归档：2026-09.md
```

## 六、设计层面必写项（最容易失传的隐性知识）

以下内容是代码里散落各处、迭代几轮后必然失传的，必须显式写清，不能只写"有个战斗系统"：

- **职责边界**：这个系统负责什么、**明确不负责什么**，防止功能漂移和职责重叠。
- **系统间交互意图**：谁在什么时机通知谁，为什么选择广播而不是直接调用，解耦带来什么好处。
- **玩家可感知的状态流转**：菜单 / 探索 / 战斗 / 暂停 / 结算等状态的进入与退出条件，谁持有状态。
- **玩法规则与边界情况**：规则本身、例外处理（如同时触发多个效果时的优先级）、失败与胜利条件。
- **数值框架**：属性维度、成长曲线、经济循环、平衡基调与调参方向。
- **进度与存档策略**：存档哪些内容、版本兼容原则、旧档如何处理。
- **内容组织维度**：关卡 / 角色 / 道具 / 敌人的分类依据与扩展方式。
- **表现与反馈约定**：美术风格、音频风格、打击感与反馈基调。
- **扩展点与预留**：已知的未来方向、目前刻意不做的事。

## 七、文档格式通用约定

- 每篇开头写元信息：最后更新日期 / 关联系统 / 状态（草案 · 生效 · 已废弃）。
- 每篇结尾保留 **「未决问题」** 区块：记录发现的矛盾、待定项。不阻塞当前任务，但必须留痕。
- 已废弃的设计**不直接删除**：标注"已废弃（原因 + 替代方案 + 日期）"，或移入 `4-决策记录/`。
- 文档之间用相对链接互相引用，不做内容复制。
- 需要指向具体系统时，只写系统名或场景名，**不写路径、不写文件名**。

## 八、冲突处置流程（发现矛盾时的固定动作）

**冲突判定**（满足任一即为冲突）：
- 新改动导致**玩法规则**与 `0-设计/核心玩法.md` 已有描述矛盾；
- 两个系统的**职责边界出现重叠或真空**；
- 数值改动破坏了已记录的**经济循环或平衡基调**；
- **流程断裂**：某状态下无可达路径，或状态流转条件自相矛盾；
- 进度结构变更导致**旧存档无法兼容且无迁移方案**。

**处置步骤**：
1. **立即停止写入文档**（已完成的改动保留）；
2. 列出冲突点：**旧设计 vs 新设计 + 影响范围（哪些系统、哪些文档受影响）**；
3. 向用户提问并给出选项：① 采用新设计并同步更新文档 ② 回退改动 ③ 记为 ADR、保留过渡期；
4. **用户拍板前不修改任何文档**，把待决项挂进「未决问题」区块。

## 九、边界（明确禁止）

- 不写脚本路径、节点路径、文件名、目录层级等代码结构信息。
- 不写函数名、变量名、信号签名、参数列表、`@export` 字段、uid 引用。
- 不把实验中、未跑通的内容写成既定设计。
- 不自动删除任何既有文档或章节。
- 不写"可能""也许""应该是"这类推测性描述。
- 不粘贴大段代码或配置片段。
- 不记录随环境变化的实现细节。

## 十、收尾自检清单

完成文档更新前逐条确认：

- [ ] 全文**不含**路径、文件名、函数/变量名、信号签名等代码结构信息；
- [ ] 用的是玩家/策划能读懂的语言，而非实现术语；
- [ ] 系统职责边界写清了"负责什么、不负责什么"；
- [ ] 新建文档已登记进 `README.md` 索引；
- [ ] `5-变更日志/` 已追加本次条目；
- [ ] 没有引入与既有文档矛盾的表述；
- [ ] 未越级：L1 改动没有顺手重写设计文档。

## 十一、模板索引（按需加载，禁止一次性全读）

模板以独立文件平铺在本技能目录下。**先判定本次要更新哪些文档，再只读对应的模板文件**；不要为了"保险"把所有模板都读一遍。

### 0-设计

| 要写/更新 | 读取模板 | 典型触发 |
|---|---|---|
| 项目全貌、卖点、范围 | `模板-游戏概述.md` | 新建项目、方向调整 |
| 核心循环、规则、胜负、节奏 | `模板-核心玩法.md` | 玩法规则改动、新增行为 |
| 属性、成长曲线、经济循环 | `模板-数值框架.md` | 新增属性维度、调整成长节奏 |
| 美术/音频基调、反馈强度 | `模板-表现风格.md` | 风格调整、新增反馈类型 |
| 世界观、叙事载体 | `模板-叙事与世界观.md` | 有叙事需求的游戏；无则标注"不适用" |

### 1-架构

| 要写/更新 | 读取模板 | 典型触发 |
|---|---|---|
| 系统清单、职责边界、依赖方向 | `模板-系统总览.md` | 增删系统、职责重划、增删全局服务 |
| 谁在何时通知谁、解耦取舍 | `模板-系统交互.md` | 新增监听关系、改动协作方式 |
| 流程与状态流转 | `模板-游戏流程.md` | 新增状态、改动切换条件 |
| 存档内容、版本兼容 | `模板-进度与存档.md` | 存档结构变更、新增存档时机 |

### 通用

| 要写/更新 | 读取模板 | 典型触发 |
|---|---|---|
| 索引导航 | `模板-README索引.md` | 首次建库、新增文档需登记 |
| 某个玩法系统 | `模板-玩法系统.md` | 新增/调整系统（**高频**） |
| 内容分类与素材规格 | `模板-内容规范.md` | 新增内容类型、改分类维度 |
| 重大决策留痕 | `模板-决策记录.md` | **仅 L3 改动**创建 ADR |
| 变更留痕 | `模板-变更日志.md` | 每次整理都要追加（含 L1） |

### 加载优先级

1. 每次整理**先读**目标文档目录里的 `README.md` 索引，确定改动落点；
2. 按上表读取**本次涉及的**模板（通常 1-3 个）；
3. `模板-变更日志.md` 几乎每次都要读；`模板-决策记录.md` 只在 L3 时读。

## 十二、配套钩子（决定"自动"能否真正落地）

技能不会自己触发。在项目根 `AGENTS.md`（或 `CLAUDE.md`）中加入一行：

> 每轮任务收尾时，加载并执行 `项目文档自动整理` 技能，按分级策略同步 `1项目文档/`。
